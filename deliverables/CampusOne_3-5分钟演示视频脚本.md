## 完整旁白

### 1. 定位

大家好，我们的作品是 CampusOne 可信校园事务智能体。它不是一个只会聊天的问答机器人，而是一名嵌入真实流程的数字协作员工：会理解，会整理，会解释，但不会越权审批。

### 2. 痛点

我们从校园场地申请切入。学生不知道材料和规则，审核人反复核对字段、附件与退回意见，管理者又缺少版本、规则命中和模型运行记录。问题不在没有表单，而在理解、核对、解释和责任边界没有一起设计。

### 3. 原则

CampusOne 把工作分成三层。大模型负责自然语言理解、整理和解释；程序负责事实、规则、权限和状态机；人工负责最终判断。模型可以替换，但责任边界不会随模型能力变化而漂移。

### 4. 闭环

产品实现了完整事务链：学生填表并预检，提交后由审核人开始审核；不符合条件时退回，学生创建 V2 修订，再次提交、批准并办结。每一步都关联角色、状态、版本和事件证据。

### 5. 产品

这不是静态原型。Web 产品包含固定演示数据、一键重置、学生与审核人动作、规则证据、版本时间轴和故障注入。即使没有 API Key，Mock 模式也能稳定复现完整演示；后续可安全切换真实模型。

### 6. 架构

系统分为交互、领域、Agent、知识和数据五层。正式状态写入只发生在领域层，Agent 只获得完成当前任务所需的最小上下文，并返回结构化输出。密钥只存在服务端环境变量，不进入浏览器或代码仓库。

### 7. Agent 契约

我们没有构建高权限自治 Agent，而是设计了三个窄任务：表单助手整理说明，审核摘要排列已验证证据，退回文案只改写程序已经确认的原因。三项任务都不能自动保存、发明规则或做出正式审批。

### 8. 规则

必填字段、容量、起止时间、开放时段和场地冲突，都由确定性规则判断。界面同时返回规则编号和事实证据。例如人数超过容量时，CAP-001 明确失败并阻止提交，而不是让大模型猜测是否合规。

### 9. 版本

退回不会覆盖原申请。V1 保留原始事实和退回理由，学生修改后生成 V2。事件时间轴追加记录创建、预检、提交、审核、退回、修订、批准和办结，因此结论能够回到当时的操作者和版本。

### 10. 故障

安全能力可以现场证明。模型返回非 JSON 会被结构解析拒绝；引用不存在的规则会得到 RULE_NOT_FOUND；超时则启用固定模板。所有错误都会写入 AI 运行记录，但正式事务状态保持不变，人工仍可继续处理。

### 11. 验证

我们只展示已经执行的结果：十三项单元测试全部通过，完整状态闭环和幂等性人工验收通过，三项 WebMCP 工具契约通过，生产构建通过，依赖审计没有 Critical 或 High 风险。真实用户试点尚未执行，因此没有虚构效率比例。

### 12. 创新与价值

创新不在让模型做更多，而在让每个结论都可验证、每个高风险动作都可控。双控制面、证据化 Agent、可演示的故障路径和可复用治理结构，使它能够迁移到设备借用、证明申请和访客预约等校园事务。

### 13. 路线

下一步先邀请三到十名用户建立填表时长、首次通过率、退回次数和审核时长基线；获得学校授权后再接入统一身份、OA 和真实场地数据；完成合规评审后，才复制到新的校园事务场景。

### 14. 收束

CampusOne 想证明的是：智能体可以真正进入校园业务，同时始终保持可运行、可审计、可降级和可复制。AI 理解，程序判定，人工确认。谢谢。

## 真人录屏替换建议

如要进一步提升参赛效果，保留片头、架构、测试和结尾页，将 1:14–3:18 替换为真实录屏：一键重置 → AI 整理表述 → 容量规则失败 → 修正并提交 → 审核退回 → 创建 V2 → 批准办结 → 注入 `rule_999` 并展示 `RULE_NOT_FOUND`。录屏时不得展示 API Key、浏览器密码或真实个人数据。
