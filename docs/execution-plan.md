# CampusOne 优化执行计划

## 目标与取舍

初赛不追求连接所有校园系统，而是把一个高频场景做成可运行、可解释、可验证的闭环。平台、模型和框架均不是评分前提；核心交付是运行效果、创新价值、设计完整度与可复现证据。

## 四阶段路径

| 阶段 | 目标 | 完成条件 | 当前状态 |
| --- | --- | --- | --- |
| S0 可信样板 | 场地申请完整闭环与安全边界 | 规则、状态机、版本、事件、Agent 降级均可演示 | 已完成 |
| S1 提交收口 | 文档、PPT、视频和身份信息一致 | 赛事约束通过，材料完整 | 团队已确认；邮箱、Word 更新与视频待完成 |
| S2 小规模试点 | 用真实样本验证易用性与价值 | 3–10 人原始记录和四项业务基线 | 待团队执行 |
| S3 校内接入 | 对接身份、OA 和场地数据 | 获得授权并完成安全合规评审 | 赛后推进 |

## 为什么这样调整原计划

1. 将“学习完所有培训”改为“按交付问题索引学习”。先看赛制、评分、提交和答辩相关内容；平台操作视频只有在决定使用该平台时才看。
2. 将“大而全 Agent”改为三个窄任务契约，规则判断和状态写入始终留在程序控制面。
3. 将“先接真实系统”改为“先用模拟数据证明闭环”，避免权限、隐私和接口审批拖垮初赛进度。
4. 将“口头说明可靠”改为“直接演示失败路径”，用非 JSON、虚假规则和超时证明系统不会越权。
5. 将身份信息集中到 `competition.config.json`，避免 Word、PPT 和脚本多处手改后不一致。

## 提交前最短路径

1. 补齐 `competition.config.json` 的联系邮箱；单位、成员和指导教师已经用户确认。
2. 运行文档和幻灯片构建器，复核封面与元数据。
3. 按现有脚本录制真人讲解与实机操作，成片必须控制在 3–5 分钟。
4. 在全新环境执行安装、lint、当前自动化测试套件和生产构建。
5. 核对上传要求，生成 SHA-256，提交后再打最终 Git 标签。
